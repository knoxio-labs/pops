# Transaction Classification

> Status: Not started — tracked in [#3607](https://github.com/knoxio/pops/issues/3607) (supersedes #3617, closed as folded in). Full-scope rework: expanded taxonomy, rule-driven classification, and paired-transfer detection ship as one program rather than an incremental cut.

Every imported transaction gets its `type` today from a 6-line heuristic (`transfer-classifier.ts`): negative amount + one of six hardcoded keywords → `transfer`, everything else falls through to the entity/AI ladder and defaults to an expense. This PRD retires that heuristic entirely and makes the existing correction-rule engine (`transaction_corrections`) the single, auditable, user-fixable classifier for transaction type. It expands the type taxonomy so positive-amount transactions stop collapsing into "income," and adds a paired-transfer detector that identifies inter-account movement structurally — matching amounts across accounts — instead of by keyword guessing.

## Problem & Context

- **Amount sign is not a classifier.** `isTransferOrIncomeRow` gates on `amount < 0` before even checking keywords, so every positive-amount row skips the transfer check by construction. Refunds, reversals, transfers, loans, rebates, and ATO/tax credits are all positive yet semantically distinct — a sign gate cannot separate them, and the code never tries.
- **A hardcoded regex is not auditable or user-fixable.** `TRANSFER_KEYWORD_PATTERN` still matches bare `payment` — `"E-TOLL PAYMENT PARRAMATTA"` types as `Transfer` and skips entity matching entirely, even though an E-Toll entity exists (CF011 / #3617). The owner cannot correct this without a code change and a redeploy.
- **The stored taxonomy is too small.** `TransactionTypeSchema` is `purchase | transfer | income` in both `rest-corrections-schemas.ts` and (independently re-declared) `rest-imports-schemas.ts`. Nothing in the system can express "this positive amount is a refund, not income."
- **Positive-amount rows silently default to the wrong type today.** At commit (`execute-service.ts` `resolveTransactionType`) and at reclassify (`reclassify-existing.ts` `deriveNewType`), any transaction whose `transactionType` wasn't explicitly set by a correction rule collapses to `'Expense'` — regardless of amount sign. A salary deposit that matches an employer entity via the ordinary entity ladder, with no correction rule in play, commits as an **Expense**. This is not a hypothetical: it is the current, unconditional fallback.
- **Three independent call sites re-implement the same lossy 3-way collapse** (`deriveTransactionType` in `commit.ts`, `resolveTransactionType` in `execute-service.ts`, `deriveNewType` in `reclassify-existing.ts`), each translating the lowercase rule-engine enum to the capitalised `Expense`/`Income`/`Transfer` strings the `transactions.type` column has always stored — itself an **unconstrained** `text` column (`rest-transactions.ts` validates it as `z.string()`, no enum) despite the app's UI treating it as a fixed 3-value set.
- **The dashboard reproduces the same sign-is-classifier bug at the presentation layer.** `StatsGrid` computes `totalIncome`/`totalExpenses` from `amount > 0` / `amount < 0` after excluding rows where `type === 'transfer'` — so a refund inflates "income" and a loan repayment inflates "expenses," independent of anything this PRD fixes unless the aggregation is redefined against the new taxonomy.
- **Paired transfers have a schema column and no engine.** `transactions.related_transaction_id` exists today (`transactions.md`: "Links paired transfers") but no code ever populates it — it is pure CRUD plumbing, set only if a caller supplies it by hand.

## Goals

- Retire amount sign and the hardcoded keyword regex as classification signals; no code path decides `type` from either.
- Make `transaction_corrections` the sole classifier for transaction `type`, extending the type-only correction path that already exists (`applyLearnedCorrection` → `handleNoEntityCorrection`) rather than adding a parallel mechanism.
- Expand the taxonomy to a two-axis model: derived `direction` (`debit` | `credit`) for display/filtering, and a rule-assigned `type` covering `purchase, transfer, income, refund, reversal, loan, rebate, tax`.
- Add a paired-transfer detector that identifies a transfer by matching amount/sign/timing across **different accounts**, linking both sides via the existing `related_transaction_id` column.
- Every non-default classification is traceable to the rule or the pairing decision that produced it.

## Non-Goals

- **Money storage format** (integer cents) — owned by #3665. This PRD sequences after it; it does not touch the numeric representation of `amount`.
- **General match-provenance schema** (persisted `matchType`/`ruleId`/`confidence` for entity matching) — owned by #3658. This PRD depends on a provenance mechanism existing for the _type_ axis specifically but does not design entity-match provenance.
- **Rule usage-counter wiring** (`incrementTransactionCorrectionUsage` is never called) — owned by #3626. The rule-driven classifier assumes this gets fixed so `timesApplied` is meaningful; it does not re-fix the counters here.
- **#3608** (hardcoded `account: 'Amex'`) is not fixed by this PRD — it is a hard blocking dependency for the paired-transfer engine only (see Sequencing).
- AI rule-proposal prompt redesign beyond widening the enum it can emit.
- Recurring/subscription detection, category budgeting changes, multi-currency transfers (no currency field exists on `transactions`).

## Classification Model

### Two-axis design: direction × type

A flat enum forces every bidirectional concept (a loan drawdown vs. a loan repayment; a tax refund vs. a tax bill) into either duplicate values (`loan_in`/`loan_out`) or a sign-coupled guess — reintroducing exactly the defect this PRD removes. Splitting the two axes keeps amount sign doing the one job it is legitimately good for (direction) while `type` stays a free, rule-assigned semantic label that never depends on sign:

| Axis        | Values                                                            | Source                                                | Persisted?                        |
| ----------- | ----------------------------------------------------------------- | ----------------------------------------------------- | --------------------------------- |
| `direction` | `debit` \| `credit`                                               | Derived: `amount < 0 → debit`, else `credit`          | No — computed at the API boundary |
| `type`      | `purchase, transfer, income, refund, reversal, loan, rebate, tax` | Correction rule, paired-transfer detector, or default | Yes — `transactions.type` (enum)  |

`direction` is never stored: storing it would create a second source of truth that can drift from `amount`, for a value trivially derived from a column that already exists. It is exposed as a computed field on the transaction wire shape and as a `direction` list-filter that translates to `amount < 0` / `amount >= 0` server-side — no new column, no migration.

### Taxonomy

| `type`     | Typical direction(s)  | Meaning                                                                                          | May be a default?                   |
| ---------- | --------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------- |
| `purchase` | debit                 | Ordinary merchant charge                                                                         | Yes — debit + resolved entity, only |
| `transfer` | debit or credit       | Inter-account movement (own accounts)                                                            | No — rule or pairing engine only    |
| `income`   | credit                | Earned income not paired to another owned account (salary, wages, dividends)                     | No — rule only                      |
| `refund`   | credit                | Merchant reversal of a prior purchase                                                            | No — rule only                      |
| `reversal` | credit (rarely debit) | Bank/scheme-initiated reversal distinct from a merchant refund (e.g. a disputed-charge reversal) | No — rule only                      |
| `loan`     | debit or credit       | Loan drawdown (credit) or repayment (debit)                                                      | No — rule only                      |
| `rebate`   | credit                | Cashback/rebate/reward credit from a provider                                                    | No — rule only                      |
| `tax`      | debit or credit       | ATO/tax-office debit (payment/BAS) or credit (refund)                                            | No — rule only                      |

`purchase` is the **only** type a code path may assign without an explicit rule or pairing match, and only for a debit-direction row that resolves a merchant entity through the existing ladder. Every other type requires a correction rule or the pairing engine — there is no default path to `income`, `refund`, `reversal`, `loan`, `rebate`, or `tax`.

## Rule-Driven Classification

- Delete `transfer-classifier.ts` and its call (`isTransferOrIncomeRow`) from `process-transaction.ts`. No replacement heuristic — the ladder step it occupied is removed, not replaced with different code.
- `TransactionTypeSchema` becomes a single canonical definition (in `rest-corrections-schemas.ts`) re-exported by `rest-imports-schemas.ts` instead of independently re-declared — the two enums have had to be hand-kept-in-sync since #2448 and this rework is the point to stop that.
- The type-only correction path already built for `transfer`/`income` (`handleNoEntityCorrection`, `classifyCorrectionMatch`) is the mechanism — it needs no new architecture, only the wider enum and a widened `handleNoEntityCorrection` purchase-needs-entity gate (unchanged: a `purchase` rule with no entity still requires the review step to resolve a merchant; every other entity-less type is a terminal classification at the rule's existing confidence split).
- Revised ladder order: **correction rules (entity + type)** → **paired-transfer detector (transfer only)** → **entity matcher / AI (assigns entity; type defaults to `purchase` only)** → **uncertain**. Correction rules keep first precedence, matching the existing "corrections outrank everything" business rule; the pairing engine is a second-line structural fallback specific to `transfer` and never competes with rules for the other seven types.
- **Default-type policy (the core behavioural fix):** after the entity/AI ladder resolves an entity on a **debit** row with no rule/pair hit, `type = purchase`. A **credit** row with no rule/pair hit is `uncertain` **regardless of whether an entity resolves** — a matched employer entity on a salary deposit no longer silently commits as `purchase`/`Expense`; it surfaces for review until a rule exists (e.g. "this employer's deposits are `income`"). This is a deliberate transition cost, not an oversight — see Risks.
- **Retired-keyword backfill:** a one-time migration seeds type-only correction rules from the keyword list being deleted, **excluding the bare `payment` token** that caused CF011/#3617. Seed at the standard new-rule confidence (`0.5` — below the `0.7` matching floor, so the seeded rules start inactive-by-confidence rather than pre-trusted) so they participate as ordinary new rules subject to the same reinforce/decay lifecycle as anything the owner authors. `transfer`/`payid` → `transfer`; `salary` → `income`; `refund`/`reimbursement` → `refund`. The owner reviews and reinforces or deletes each as normal usage occurs.
- **Traceability:** every classification a completed import or reclassify pass produces must be attributable after commit — to a correction `ruleId`, or to the paired counterpart transaction (the `related_transaction_id` value itself is the provenance for a pairing decision, no separate id needed). This requires a persisted provenance mechanism on `transactions` (currently none exists; `ruleProvenance`/`matchedRules` live only on the in-memory `ProcessedTransaction` and are discarded at commit). See Sequencing — this PRD depends on #3658 for that mechanism rather than growing a second, overlapping one.

## Paired-Transfer Detection Engine

**Hard gate: this engine does not run against production data until #3608 ships real per-account values.** Every CSV-imported row is currently written with `account: 'Amex'` regardless of the source bank (`validateRow`, `useProcessing`, `ProcessingStep` all hardcode the literal). A `different account` predicate is meaningless — and actively dangerous — while three of four supported banks' rows are indistinguishable from Amex rows by account: it would either never fire across banks, or (if the guard were loosened) pair unrelated same-account rows. The matcher ships gated behind #3608 and stays off in production until that lands.

**Matching algorithm** — for an unmatched transaction `T` (no rule/pair classification yet, `related_transaction_id IS NULL`):

1. Candidate set: transactions `C` where `|C.amount| = |T.amount|`, `sign(C.amount) = -sign(T.amount)`, `C.account ≠ T.account`, `C.related_transaction_id IS NULL`, and `|date(C) − date(T)| ≤ window`.
2. **Window is date-granularity, not timestamp-granularity.** `transactions.date` stores `YYYY-MM-DD` only — there is no time-of-day field to compare. "Close timestamp" in the original framing means "close date" in practice; the window is a configurable number of days (default **3**, covering weekend/settlement lag), exposed as `FINANCE_TRANSFER_PAIR_WINDOW_DAYS` following the pillar's existing `FINANCE_AI_CATEGORIZER_*` env-var convention.
3. **Unique match required.** If exactly one candidate satisfies the predicate (ties broken by closest date), auto-link. If more than one candidate is equally close, do not auto-link — the transaction is left unmatched for manual resolution rather than picked arbitrarily. This mirrors the existing matched/uncertain split rather than inventing a third state.
4. **Linking** reuses the existing `related_transaction_id` column: both sides are set to each other's `id` — a symmetric 1:1 link, not a directional parent/child — and both sides' `type` is set to `transfer`. No new `pair_id` column is needed; the column already models this correctly, it has simply never been populated automatically.
5. **Entity handling:** transfers are entity-less by convention (matching today's `buildMatchedTransfer`, which sets `matchType: 'none'`). The pairing engine does not assign an entity, and only clears a previously-assigned entity when the pair match is unambiguous (unique candidate) — it must not repeat the #3612 defect (retroactive reclassification silently null-clearing entities on a shaky match). Fix #3612's gate before or alongside this engine; both are "touch historical rows in the background" mechanisms and must share the same safeguard.
6. **Two trigger points:** (a) at import commit, matched against both the current batch and existing committed rows; (b) a scheduled reconcile pass for rows imported before their counterpart existed. The reconcile pass is its **own** worker (e.g. `reconcile-paired-transfers.ts`), built on the same injectable-lookup, testable-`runOnce` shape as `reconcile-cross-pillar.ts` — it is not folded into that worker, which reconciles budgets' `owner_uri` staleness against the registry pillar, an unrelated domain.
7. **Idempotency:** a transaction with a non-null `related_transaction_id` is never re-evaluated by either trigger; the match-and-link write for a given pair happens inside one DB transaction so two concurrent passes cannot each link one side to a different candidate.

## Sequencing & Dependencies

- **#3665 (money as integer cents) ships first.** Both programs touch the `transactions`/`corrections` schema files; landing the cents migration and the type-enum migration in the same window multiplies merge/regression risk for no shared benefit. Do the amount-representation change first, then migrate the type enum against the settled schema.
- **#3608 (real per-account values) blocks only the paired-transfer engine**, not the rest of this PRD. The taxonomy expansion and the rule-driven classifier ship independently of it; only the pairing engine's production rollout is gated on #3608.
- **#3626 (rule usage counters) is a soft dependency.** Once `transaction_corrections` is the sole classifier, `timesApplied`/`lastUsedAt` are the only signal for which rules are load-bearing vs. dead weight — currently they never increment. Fix independently, ideally before or alongside this PRD, so the new classifier isn't shipped onto still-broken telemetry.
- **#3658 (persisted match provenance) is a soft dependency for the traceability goal.** "Every classification is traceable to the rule or engine that produced it" only holds after commit if the row itself carries that provenance — today it does not, and #3658 is where that mechanism is designed. Land it first, or fold its minimal `type`-scoped subset into this PRD's migration rather than shipping two independent provenance schemes.
- **#3612 (reclassify bypasses the classification gate) should land before or alongside this PRD.** `reclassifyExistingTransactions` force-applies any ≥0.7 rule match with no matched/uncertain gate and silently null-clears entities — the exact class of bug the paired-transfer reconcile pass must not inherit, since it does the same "retroactively touch historical rows in the background" thing.
- Recommended internal order: (1) canonical enum + schema/contract migration + legacy backfill, (2) rule-driven classifier replacing the heuristic (deletable independently, no pairing dependency), (3) paired-transfer engine, gated behind #3608.

## Risks

- **Lossy historical backfill.** `Expense → purchase` for every legacy row loses any chance of recovering a true `refund`/`loan`/`tax` retroactively from a flat capitalised string. Mitigation: run `reclassifyExistingTransactions` again once the owner has authored rules covering their common non-purchase patterns — full historical accuracy is not guaranteed, only forward accuracy.
- **Review-volume transition cost.** Moving from "any entity match commits" to "an unmatched credit is always `uncertain`" means recurring credits (salary, standing rebates) surface for review until the owner authors rules for them — a one-time cost, not a permanent regression, but real during rollout. Mitigate by seeding rules for the owner's known recurring income patterns as part of the launch, not waiting for organic discovery.
- **Paired-transfer false positives.** Two unrelated transactions can coincidentally share `|amount|`, opposite sign, different accounts, and a close date (e.g. two unrelated $50 charges). The ambiguous-match suppression (never auto-link a non-unique candidate) reduces but cannot eliminate this for a genuinely coincidental unique pair; a user-facing unlink action must exist.
- **Background reconciliation touching historical data** carries the same risk class #3612 documents for rule reclassification — the pairing reconcile pass must not silently clear a previously-`matched` entity or override a reviewed classification without an unambiguous signal.
- **Date-only granularity widens false-positive risk** for high-volume accounts with multiple same-day, same-amount, opposite-sign transactions across different banks — there is no time-of-day field to disambiguate further without a separate CSV-format change, which is out of scope here.
- **Wide blast radius in one program.** The enum touches contract, generated OpenAPI, generated FE client, DB schema, three now-deleted collapse functions, and dashboard aggregation simultaneously. Sequencing after #3665 reduces but does not eliminate the regression surface; the internal ordering above (schema → classifier → pairing) is intended to keep each landable PR small despite the program being large.
- **Rule-authoring surface area grows 3→8 values.** The correction rule manager's type dropdown and the AI rule-proposal prompt (`ai-propose.ts`, `ai-feedback.ts`) must be updated in lockstep or the AI proposer keeps emitting only the legacy three, silently limiting what users can teach it.

## Acceptance Criteria

- [ ] `TransactionTypeSchema` is a single canonical definition (in the corrections contract) re-exported by the imports contract — not two independently-declared `z.enum` literals — and covers exactly `purchase | transfer | income | refund | reversal | loan | rebate | tax`.
- [ ] `transaction_corrections.transaction_type` and `transactions.type` are both sqlite text-enum columns constrained to the same 8 values; `transactions.type` is no longer an unconstrained free string.
- [ ] `rest-transactions.ts`'s list/get/create/update schemas validate `type` against the canonical enum instead of `z.string()`.
- [ ] `direction` (`debit` | `credit`) is derived from `amount` sign at the API boundary and is never persisted as its own column; a `direction` list filter is available and translates to an amount-sign predicate server-side.
- [ ] Existing `transaction_corrections` rows with `transaction_type` in `{purchase, transfer, income}` remain valid, unchanged, under the expanded enum.
- [ ] Legacy `transactions.type` values are backfilled (`Transfer→transfer`, `Income→income`, `Expense`/`''→purchase`); no row is left with a value outside the 8-value enum after migration.
- [ ] `transfer-classifier.ts` and its call site in `process-transaction.ts` are deleted; no code path decides `type` from amount sign or a hardcoded keyword regex.
- [ ] A transaction's `type` is set only by: a matched/reinforced correction rule, the paired-transfer detector, or the `purchase` default applied strictly to a debit row with a resolved merchant entity.
- [ ] A credit-direction row with no correction match and no paired-transfer match lands in `uncertain` regardless of whether an entity resolves — never silently defaulted to `income` or any other type.
- [ ] The retired keyword list is back-filled as starter correction rules at the standard new-rule confidence (0.5), excluding the bare `payment` token that caused CF011/#3617.
- [ ] `deriveTransactionType`, `resolveTransactionType`, and `deriveNewType` are removed; the classified `type` is written verbatim at commit and at reclassify.
- [ ] A pair is detected when two transactions have equal absolute amount, opposite sign, different `account`, and fall within a configurable date window (default 3 days, `FINANCE_TRANSFER_PAIR_WINDOW_DAYS`).
- [ ] A unique (non-tied) candidate within the window auto-links both sides via `related_transaction_id` (symmetric) and sets both sides' `type` to `transfer`.
- [ ] Multiple equally-close candidates within the window are never auto-linked; the transaction is left unmatched for manual resolution.
- [ ] The pairing engine never overwrites an existing entity assignment on an ambiguous (non-unique) candidate.
- [ ] Pairing runs both at import-commit time (current batch + existing rows) and via a scheduled reconcile pass, implemented as its own worker (not folded into `reconcile-cross-pillar.ts`).
- [ ] A transaction with a non-null `related_transaction_id` is never re-evaluated or re-linked by either the commit-time or reconcile-time pass.
- [ ] The paired-transfer detector is feature-gated off in production until #3608 ships real per-account values.
- [ ] Correction rules take precedence over the paired-transfer detector — a rule-classified transaction is never re-evaluated by the pairing engine.
- [ ] Every classification a completed import or reclassify pass produces is traceable after commit to either a `ruleId` or a paired counterpart transaction id.
- [ ] `reclassifyExistingTransactions` and the new pairing reconcile pass both route through the matched/uncertain confidence gate (no force-applying a sub-threshold match, no silent entity null-clearing) — closing #3612 for both mechanisms.
- [ ] The dashboard's income/expense aggregation uses an explicit type→tile mapping instead of `amount sign` + `type !== 'transfer'`.
- [ ] The transactions list type filter, the correction-rule editor's type dropdown, and the AI rule-proposal prompt all offer the full 8-value taxonomy.
- [ ] The regenerated OpenAPI spec and Hey API FE client reflect the 8-value enum with no manually hand-patched generated file.
- [ ] This PRD's schema migration lands after #3665's money-representation migration, not concurrently.
- [ ] Every new classification path (rule engine, pairing engine, default-purchase fallback, uncertain-credit fallback) has a Vitest test against an in-memory SQLite instance covering at least one case per taxonomy value plus the ambiguous-pair and no-match cases.
