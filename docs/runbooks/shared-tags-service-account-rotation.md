# Shared-tags service-account rotation

> Operator-only procedure for the POPS-5417 rollout, after its release and change approvals. This page is not authorization and does not record that any production action has happened.

## Approval and scope gate

The Registry service-account admin API is user-only and supports `GET /service-accounts`, `POST /service-accounts` (create and mint), and `POST /service-accounts/:id/revoke`. It has no in-place scope-update route. A grant change therefore uses a replacement account. Do not edit Registry SQLite directly.

Obtain explicit owner approval for every added scope before creating an account. `tags.tags` is the requested narrow vocabulary scope; this runbook does not approve it for production. Do not substitute the broader `tags` grant. Scope matching is by dotted prefix ([implementation](../../libs/sdk/src/server/service-account-scope.ts)): `tags.tags` permits the vocabulary namespace, while `tags` permits every `tags.*` procedure. `finance.tagged` and `purchases.tagged` cover their respective tagged routes, not the whole Finance or Purchases API.

For every existing account, first read its complete current scope list from Registry and preserve that list during replacement. The Finance and Purchases arrays below are the grants their current source declares; if a Registry account differs, stop and reconcile with the owner before minting. MCP has no single source-declared whole-account scope array: preserve its Registry list and add only the approved route scopes shown.

## Replacement sequence

1. **Confirm recovery.** Through the Registry's user-only list route, record each target account's exact name, ID, active state, and complete scope list in the restricted operator change record only; do not put real account IDs or key values in this repository or a public PR. Verify the Registry's normal backup and recovery path. Record a recoverable version of each current host secret and its consumer configuration in the approved secret store; record the version/reference, never the key value. Confirm the previous secret can be restored.
2. **Choose the replacement identity and complete grant.** For an existing account, select a new unique name and construct its full scope list from the listed grants plus only the approved additions. Registry account names are unique across active and revoked rows and cannot be reused. For the new Orchestrator account, use the source-pinned name `orchestrator` only if the Registry list confirms it is unused; if it already exists, stop and resolve the ownership/state rather than minting a duplicate.
3. **Create and capture under human control.** A human operator with a verified Cloudflare Access session uses the Registry admin route through the Shell proxy. In production, confirm Cloudflare Access team validation is configured before proceeding. `POST /service-accounts` returns `plaintextKey` once. Use an approved capture method that writes the value directly into the restricted host file-secret or Ansible Vault entry without rendering the response in a terminal or log. If secure capture is unavailable, stop before the request.
4. **Install without retiring the old account.** Update the matching mounted secret through a reviewed homelab change and the normal release process, using the consumer reference in the table. Orchestrator, Finance, and Purchases use `POPS_INTERNAL_API_KEY_FILE`; MCP uses `POPS_API_KEY_FILE`. Keep the old account active and the prior secret version available for rollback.
5. **Verify the replacement.** Confirm the new account is active with exactly the approved scopes; start or restart the consumer through the approved deployment process; verify service health and every required downstream operation. Use only an approved test target for writes such as tag attach/detach. Do not expose the key while testing.
6. **Revoke only after success.** Once the consumer is healthy and all required operations pass, revoke the old account by its exact Registry ID. Verify the new account remains active, the old account is revoked, and the consumer still works. Retain the previous secret version for the approved recovery period.

## Rollback

If the new consumer fails before the old account is revoked, restore the previous secret version and consumer configuration, restart through the normal release path, and verify the old account still works. Leave the old account active; do not try to restore Registry SQLite or patch the scopes in place. Record the unused replacement ID for operator follow-up. If the old account has already been revoked, the API has no un-revoke operation; recovery requires another approved replacement rotation.

The one-time key and any Access token must stay out of shell history, console output, process logs, compose values, this repository, Huly, and chat. Only the authorized human operator handles key capture and installation.
